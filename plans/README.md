## Dependency notes

- **002 depends on 001** because 002's done criteria is "zero typecheck errors",
  and 3 of the original 51 errors *are* the three shipped crashes. Running 002
  first means re-deciding triage on code 001 is about to change.
- **001 and 002 are the gate.** Every other plan lists `npm run typecheck` in its
  done criteria, so all of them gain a real compiler check once 002 lands. Do
  them first even though they are not money bugs — the missing typecheck is
  demonstrably why the crashes in 001 shipped.
- **006 depends on 005** because plan 005 redefines
  `process_withdrawal_completion`, whose transition guard is what makes 006's
  rewind exploitable. Apply 005, then re-verify 006's step 7. Plan 005 does
  **not** remove that guard, so 006 is still required.
- **003, 004, 005, 007 are mutually independent** and can be executed in
  parallel by different agents — with one hard constraint below.

### Migration ordering constraint (004, 005, 006)

Three plans add a file to `supabase/migrations/`. Each **must** generate its
filename with `npx supabase migration new` at execution time, and the three must
be **applied in timestamp order**. Do not hand-reuse a timestamp. A prior
collision is already in the repo history —
`20260921000004_allow_enroute_order_status.sql` exists only because of one
(commit `c8231ca`).

None of these migrations can be applied from this environment: there is no local
Supabase instance, and `supabase db push` is blocked by a known ~76-row
local/remote migration-history drift (recorded in
`.scratch/audit-remediation/issues/03-edge-function-payment-holes.md:30-33`).
**Applying them is a human task on a staging database.** Each plan's step 7
lists the role scenarios to verify.

## Findings considered and rejected

Recorded so they are not re-audited next run.

- **Test suite 51.6s wall-clock** — not worth doing. Per-file times are 5–163ms;
  the overhead is cumulative jsdom setup across workers. Revisit only after a CI
  exists and becomes the inner loop.
- **`src/lib/utils.ts` (50 fan-in)** — reported as a possible "utils junk
  drawer". It is a clean 6-line `cn`. No finding.
- **Circular imports** — reported as an architecture risk. Zero found across all
  259 source files.
- **React Query "major version lag"** — 5.x is current. The real issue is that
  it is mounted as a `QueryClientProvider` but never used (`useQuery`,
  `useMutation`, `queryKey` appear nowhere in `src/`). That is a dead-dependency
  cleanup, not lag.
- **Tailwind 3→4, Vite 5→8** — real lag, zero observed breakage in the code.
  Novelty-only; not reported.
- **`restaurants` cross-tenant read** (`USING (true)` on a table still used as
  the tenant key in `revenue_sharing`, `deliveries.restaurant_id`,
  `wallets.party_id`) — **real finding, deliberately not planned.** Several
  legacy policies key off `restaurants.manager_user_id`, so tightening it in
  isolation risks RLS recursion/deny. Needs its own plan that sequences the
  `merchants` policy pattern (already applied in `20260918073500`) across the
  dependent policies first.
- **Money-formatting consolidation** (43 raw `D${n.toFixed(2)}` sites, two
  spacing conventions, 4 competing formatters) — real, but the subagent's *S /
  LOW* estimate was wrong: `graphify affected formatMoney` returns **degree 82
  across ~30 files**. Re-estimated M / MED. Deferred until the typecheck baseline
  makes a 30-file refactor verifiable.
- **Settlement page recomputes money in the browser** (`SettlementsPage.tsx:623-627`
  omits the fuel term and the `GREATEST(…, 0)` clamp that
  `credit_wallets_on_settlement` applies) — **the highest-value deferred
  finding.** Approvers currently approve and export CSVs whose Rider/Merchant/platform
  columns do not match `wallet_transactions`, and the success toast quotes a "net"
  figure that was never transferred. Effort L, risk HIGH. Needs a
  `settlement_preview()` RPC mirroring the existing `payment_reconciliation_report`
  pattern. It collapses a class of bugs rather than patching one, which is why it
  is worth its own plan rather than being folded into these seven.
- **Three tracked lockfiles + `--legacy-peer-deps`** — real, but the flag is
  currently masking a genuine React 18 / `react-leaflet@5` peer conflict
  (`npm ls react` reports `invalid: "^19.0.0"`). Removing it before resolving the
  conflict breaks the Vercel build. Deferred as its own dependency-hygiene plan.
- **`supabase/functions/settlement-e2e` is unreachable** — the only test that
  executes real settlement money math, excluded from `vitest.config.ts`'s
  `include` glob, with no runner script, and **Deno is not installed** in this
  environment. Recorded in `docs/testing.md` by plan 002. Wiring it up needs a
  Deno toolchain decision first.
- **288 of 800 tests are migration-text greps** (`readFileSync` + `toContain`) —
  legitimate in spirit (the migration *is* the security boundary when there is no
  DB in CI) but a change-detector rather than a contract. Notably
  `settlementDualMode.test.ts:55-58` blesses a **silent** `RETURN NEW` as correct.
  Converting the top invariants to executed assertions against a throwaway
  Postgres is high value and needs new CI infrastructure.
- **10+ additional security findings** surfaced by the audit and **not planned**,
  because each needs its own verification: the `PUBLIC` EXECUTE grants on 20+
  `SECURITY DEFINER` functions (measured: 142 `SECURITY DEFINER` vs 11
  `FROM PUBLIC` revokes); the public `receipts` bucket; missing
  `file_size_limit`/`allowed_mime_types` on every bucket; the unvalidated `?next=`
  redirect on sign-in; `Capacitor` shipping against a `*.lovableproject.com`
  preview origin with `cleartext: true`; finance/admin routes gated by
  authentication rather than role; the browser-only `withdrawal_pin` check; raw
  internal error text returned from the `verify_jwt = false` edge functions; and
  dispatch RPCs (`claim_delivery`, `reject_delivery`, `widen_dispatch_pool`)
  that accept arbitrary delivery ids.

## A manual action item, not a plan

`.env~` in the repo root is an untracked editor backup containing **live**
credentials by type: a payment-provider secret key and webhook secret, a
database password, a `service_role` key, a Supabase access token, a GitHub PAT,
and a Vercel token. It is correctly gitignored and untracked, so it is not
committed — but values are burned by exposure regardless, and the file is
gitignored rather than absent, so a `git add -f` or a repo zip would commit it.

**Rotate, then delete.** Values are intentionally not reproduced anywhere in
these plans. Adding `gitleaks` as a pre-commit hook would prevent a recurrence
and is a cheap addition to plan 002's CI work.
